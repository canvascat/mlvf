# 专辑发布 CLI

日期：2026-11-19  
状态：待实现

把每次手写的串行导出、抽封面、入队、建合集、投稿收成 `nub run release`。备料和预览仍用现有命令。

## 目标

- 单首导出成功后抽封面并写入 `tmp/upload-queue.json`，不投稿。
- 单首投稿只处理指定的一条，成功后加入已写明的合集小节。
- 批量有两种：全部导出完再投稿；导出一首就入队一首，并在投稿间隔允许时马上传。
- 两种批量只处理这一张专辑本次入队的条目。
- 投稿间隔、限流、草稿、Hi-Res、动态和合集写操作遵守 `AGENTS.md`。
- 命令在当前终端前台跑，不用 `nohup`、`disown`，也不在命令末尾加 `&`。

## 非目标

- 不改备料规则，不改 `album-preview`。
- 不在空闲窗口自动投稿。`hold_until` 不由本 CLI 改写，也不用来挡住用户明确发起的投稿。
- 不投稿队列里其他专辑的 `pending`。
- 不并行渲染。导出始终 1 路。
- 不并行投稿。同一时间只有一首在传。

## 命令

入口：`package.json` 的 `release` 脚本，运行 `src/release/cli.ts`。

```console
nub run release -- export <配置.json>
nub run release -- upload <队列 id 或成片路径>
nub run release -- season <备料目录>
nub run release -- export-then-upload <备料目录>
nub run release -- export-and-upload <备料目录>
```

曲序：读备料音频的 `track` 标签，从小到大。没有标签时按 json 文件名的 `zh-Hans` 排序。

已有成片且用户没说重导时，导出跳过该首，仍补封面和队列条目。`--overwrite-video` 才覆盖已有 mkv。

## 队列

文件仍是 `tmp/upload-queue.json`。没有文件时建成 `{ "locked_since": null, "hold_until": null, "items": [] }`。

一条专辑条目至少有 `id`、`mode`、`status`、`video`、`title`、`created`、`upload`。`id` 用 `release-<备料目录名的稳定短哈希>-<两位曲序>`。同一成片路径已有 `pending` 时更新那一条，不另加。已是 `done` 或 `draft` 的不重置。

`upload` 含 `title`、`desc`、`tag`、`cover`、`tid`（130）、`copyright`（1）、`dynamic`、`hires`。标题和简介读备料目录里同名 `.txt`。封面 jpg 与成片同名，放在成片旁边。有歌词时用 `nub tmp/lyric-cover-time.ts` 取秒数再抽帧；没有歌词时抽第 2 秒。

Hi-Res：看封装进成片的那条音轨。无损且采样率不低于 96 kHz，或采样率不低于 48 kHz 且位深不低于 24 bit 时 `hires` 为 1。44.1 kHz / 16 bit 和有损音轨为 0。

动态只给曲序第一首，内容是 `<歌手>《<专辑名>》整张专辑`。这一张里已经有动态时不再改。

新条目 `mode` 为 `first`。更新已有条目时保留原来的 `mode` 和 `bvid`。

## 导出后上传

`export-then-upload`：

1. 按曲序导出。每首成功后抽封面并入队。
2. 导出阶段不投稿。
3. 某一首导出失败则停住，不开始投稿。
4. 全部导出成功后，按曲序投稿这一批 `pending`。

## 导出并上传

`export-and-upload` 在同一进程里跑两个工人，共享这一批的队列视图。

导出工人按曲序导出。每首成功后抽封面、入队，并通知投稿工人。某一首导出失败则不再导出后面的，已经入队的继续按下面的规则投稿。

投稿工人在每次「一首导出完成」或「一首投稿结束」时检查：

1. 若已有投稿在进行，这次检查不做第二首。
2. 取这一批里成片已落盘、`status` 为 `pending`、曲序最前的一条。
3. 没有这样的条目：导出还没结束就继续等；导出已经结束就退出。
4. 距上一首投稿成功不足 180 秒就等到满 180 秒再传。还没有成功投稿过的第一首不等待。
5. 传完按结果更新队列，再立刻做一次同样的检查。

导出不等待投稿。投稿等待间隔时，导出继续做下一首。

## 合集

`season`，以及两种批量命令在导出之前：

- 标题是 `<歌手> <专辑名>`，简介是 `<歌手>专辑《<专辑名>》的歌词视频。`
- 同名合集已存在则复用。
- 小节标题用专辑名。没有小节时打开分组；默认「正片」改成专辑名。
- 把 `season_id` 和 `section_id` 写回这一批条目。
- 封面用备料目录里的专辑封面，转成 jpeg 再上传。

投稿成功并拿到 BV 后，用 `biliup season add <section_id> --vid <bvid>` 加入小节。成功的合集写操作之间至少隔 3 秒。`20111` 和 `256000` 等十几秒到一分钟，重试这一次。新稿件返回 `-404` 或「啥都木有」时隔 30 秒重试这一次，不把它当成永久失败，也不先传下一首。加入失败且已不是上述可重试情况时，队列仍标 `done` 和稿件号，`season_added` 为 false，并在终端说明。

## 投稿

必须 `biliup upload --submit web`。登录态用 `~/.config/biliup/cookies.json`。

成功的唯一标准：进程退出码 0，输出含「Web 接口投稿成功」，并且有 BV 号。

`mode` 为 `overwrite` 且有 `bvid` 时，不新投。先 `biliup append --submit web --vid <bvid>`，再用网页编辑接口只留下新的分 P，分 P 标题沿用原来的。

限流：

- `21566`：等待 180 秒，重试刚才这一首，不开始下一首。只把独立出现的 `21566` 当错误码。
- `137022`，或本批已经隔了 180 秒仍返回 `21566`、`137022` 或「投稿过于频繁」：从这一条起改存草稿，停止投稿。
- 草稿箱先 `GET /x/vupre/web/draft/list?pn=1&ps=30`。空位是 `30 - 已有条数`。空位为 0 时一条都不存，剩下的留在队列并告诉用户。能存的只存空位那么多。不删已有草稿。
- 存草稿一条一条来，上一条成功后再存下一条，至少隔 3 秒。用这次上传已经拿到的 `filename` 和 `cid`。成功后把 `status` 写成 `draft` 并记下 `draft_id`。同一次批量里不发布这些草稿。
- `overwrite` 不走草稿。

启动投稿前若已有 `biliup upload` 或另一次 `release` 投稿在跑，直接退出，不并行传。

## 模块

| 模块 | 职责 |
| --- | --- |
| `src/release/cli.ts` | 解析子命令 |
| `src/release/order.ts` | 备料目录的曲序 |
| `src/release/queue.ts` | 读写队列、按成片路径更新、只选取本批 |
| `src/release/cover.ts` | 封面秒数和抽帧 |
| `src/release/export-batch.ts` | 串行导出，跳过已有成片 |
| `src/release/upload-one.ts` | 单首投稿、限流、草稿 |
| `src/release/season.ts` | 创建或复用合集，加入小节 |
| `src/release/schedule.ts` | 导出后上传，以及导出并上传的间隔检查 |

导出调用现有 `exportVideo`。不改渲染用的浏览器和 `--gl=angle`。

## 测试

用假的导出、投稿和合集接口测调度，不真的渲染或投稿。

- 导出后上传：三首都入队之后才出现第一次投稿。
- 导出并上传：第一首导出结束就投稿；第二首导出结束时若距上次成功不足 180 秒，等到满再传。
- 投稿进行中又有一首导出完成，不并行开第二首；上一首结束后再检查。
- 只选本批 `pending`，队列里另一张专辑不动。
- `21566` 重试同一首；间隔后仍频繁则停止投稿并留下草稿状态。
- 同一成片路径的 `pending` 被更新，不新增第二条。
